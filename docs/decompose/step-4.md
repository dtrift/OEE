## Д0 (вечер до старта, ~0.5–1 ч): окружение

1. Ветка `feat/nodes-a-q` в OEE.
2. Брокер: mosquitto локально (docker или сервис); ручная проверка
   `mosquitto_pub/sub` на `oee/line1/#`.
3. `rumqttc` в `[workspace.dependencies]` корневого `Cargo.toml` (версию
   зафиксировать; дашборд недели 5 будет использовать ту же).

## Д1 (пн, ~3 ч) — узел A: пайплайн offline

1. `SimSource`: реализация `SensorSource` поверх CSV прогона симулятора
   (run-файл — источник; live-стрим — не нужен до недели 5). `Sample = f32` амперы.
2. Окна по `WindowSpec(A)` (128 @ 1.6 кГц, 80 мс) → `predict()` (модель недели 3
   через `#[model]` в `nodes`) → статус.
3. Offline-режим: узел пишет статусы в CSV (`node,run_id,t_ms,state` — схема
   `capture`); отладка без брокера.

Проверка: статусы A на прогоне `scenarios/base.toml` совпадают с ground truth
(колонка `state`); расхождения — только на границах окон.

## Д2 (вт, ~2–3 ч) — узел A: MQTT

1. Публикация (rumqttc): `oee/line1/a/status` — JSON `{state, t_ms, run_id}`;
   `oee/line1/a/meta` — версия модели, `WindowSpec`. По изменению статуса, не
   каждым тиком.
2. Гистерезис/усреднение по 2–3 окнам на границе классов (анти-флап).
3. Обрыв брокера: reconnect с backoff, узел продолжает считать и дозаписывает
   offline-CSV.

Проверка: smoke — симулятор | узел A | `mosquitto_sub -t oee/line1/a/#`; статусы
меняются по сценарию.

## Д3 (ср, ~3 ч) — симулятор: синтез tap-звука

1. События tap в сценарии: каждая деталь стучит; годность известна — ground truth
   (разд. 4).
2. Синтез: затухающая синусоида; целая — выше частота, дольше затухание;
   треснутая — ниже, быстрее + шум; параметры варьируются seeded RNG.
3. Частота 16 кГц = `WindowSpec(Q)`: окно 1024 @ 16 кГц = 64 мс. Лаборатория
   недели 4: подтвердить окно спектром тапа; если 64 мс не хватает — правится
   только в `window_spec` (единая точка правды).
4. Выгрузка: WAV-подобные буферы + CSV-мета (`t_ms, verdict`) для обучения Q.

Проверка: классы различимы спектрограммой/на слух; seed воспроизводим;
детерминизм-тест расширен на tap-канал.

## Д4 (чт, ~3–4 ч) — узел Q: модель и интеграция

1. Датасет тапов (микс годен/брак, несколько seed) → модель Q: Conv1D-семейство
   как у A, вход `(1024, 1)` → int8 → `ml/models/model_q.tflite`.
2. Узел Q: tap-буфер → окно → `predict()` → `oee/line1/q/verdict`
   (`{verdict, t_ms, run_id}`); offline-CSV — как у A.
3. Черновая confusion matrix Q на val.

Проверка: вердикты Q в брокере совпадают с truth на явных случаях.

## Д5 (пт, ~2–3 ч) — интеграция и устойчивость

1. Связный прогон: симулятор (ток + тапы) | узел A | узел Q | брокер.
2. Error isolation: битое окно/пустой буфер — warning и пропуск, узел живёт
   (правило: `raise`/паника в потоке не роняет узел целиком).
3. Прикидка темпа: predict успевает за темпом ленты (не метрика — «не хуже»).

Проверка: прогон без падений; статусы A и вердикты Q в брокере.
