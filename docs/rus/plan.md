## 0. Description для ментора (одним предложением)

**Полный вариант:**

> Курсовой проект по Rust — цифровой двойник производственной линии с измерением OEE на TinyML:
> симулятор на Rust генерирует сигнал тока станка, события ленты и звук tap-теста изделия,
> узлы-процессы выполняют инференс квантованных нейросетей через форк MicroFlow (вклад —
> реализация оператора `Conv1D`: парсер → кодеген → int8-рантайм), а OEE = Availability ×
> Performance × Quality сходится в live-дашборд по MQTT и сверяется с ground truth симулятора.

**Короткий вариант:**

> Симулятор производственной линии на Rust измеряет OEE тремя TinyML-узлами (ток, счёт, звук)
> через форк MicroFlow с реализованным мной оператором `Conv1D`; инференс — только код и QEMU,
> без железа.

## 1. Концепция и математика

### 1.1 Что такое OEE

OEE (Overall Equipment Effectiveness, общая эффективность оборудования) — стандартный
показатель в производстве: насколько эффективно станок или линия используется относительно
идеального максимума. Выражается одной цифрой от 0 до 100%:

**OEE = Availability × Performance × Quality**

Каждый множитель — отдельный вопрос к производству:

| Компонента   | Вопрос                      | Формула                          | Пример                            |
| ------------ | --------------------------- | -------------------------------- | --------------------------------- |
| Availability | Станок вообще работал?      | Run Time / Planned Time          | из 8 ч смены простоял 1 ч → 87.5% |
| Performance  | Работал на полной скорости? | (Ideal Cycle × Count) / Run Time | идеал 100 дет/ч, сделал 85 → 85%  |
| Quality      | Детали были годными?        | Good Parts / Total Parts         | из 100 деталей 3 брак → 97%       |

Пример: 0.875 × 0.85 × 0.97 ≈ **72%** OEE.

Зачем одна цифра, а не три: станок может «работать идеально», но OEE всё равно низкий —
он стоял половину смены (потеря Availability), работал медленнее номинала (Performance),
часть деталей — брак (Quality). OEE сводит три вида скрытых потерь к одной метрике для
дашборда. Ориентиры: **85%** — мировой уровень (впервые достигнут Toyota), **60%** —
типичное производство без оптимизации, **40%** — низкоавтоматизированный цех.

### 1.2 OEE в проекте

Каждая компонента измеряется TinyML-классификацией на симулированных данных:

| Компонента   | Формула                  | Узел          | Источник данных в симуляторе                                            |
| ------------ | ------------------------ | ------------- | ----------------------------------------------------------------------- |
| Availability | Run Time / Planned Time  | A — ток (ML)  | 1D-CNN по синтетическому сигналу тока: работа / холостой / заклинивание |
| Performance  | Ideal Cycle × Count / RT | P — счёт      | события «деталь прошла» от ленты (детектор фронта IR-барьера)           |
| Quality      | Good / Total             | Q — звук (ML) | синтез звука tap-теста: целая деталь звенит, треснутая — глухая         |

Итог — одна цифра OEE на live-дашборде. Ground truth известен симулятору по построению:
сравнение measured vs true OEE — главный численный результат.

## 2. Ключевые решения (что заменило железо)

- **Симулятор линии на Rust** — детерминированный (seeded RNG), воспроизводимые эксперименты.
- **Узлы — хост-процессы**: тот же пайплайн (сенсор-сим → фичи → `predict()` → MQTT), что и на
  прошивке, но без MCU; архитектура через trait `SensorSource` (`SimSource` сейчас, `AdcSource`
  в future work) оставляет дверь открытой для реального железа.
- **Параллельная колея железа** — вне критического пути: контракты в `features-cli`
  (`window_spec`, калибровка, `capture`), trait `SensorSource` и скелет `firmware/`
  (ESP32-S3) готовят обкатку на реальном стенде; сроки и гейты плана не меняются
  (подробности — README, раздел «Колея железа»).
- **QEMU (LM3S6965)** — штатная машина stock QEMU для Embedded Rust: точные flash/RAM из ELF,
  приближённые тайминги (честно указать в отчёте).
- **Без PR в апстрим**: вклад в движок живёт в локальном форке; бенчмарки и тесты — в отчёте.
- Узел Q (акустика) остаётся: синтез звука — это чистый код, датасет не надо записывать дрелью.

## 3. Архитектура цифрового двойника

```text
[line-simulator: Rust, seeded]
  машина (FSM: idle/run/jam) → сигнал тока ──→ [узел A] фичи → 1D-CNN → статус
  лента (скорость, интервалы) → события IR  ──→ [узел P] детектор фронта → счёт
  tap-тест (синтез звона) → WAV-подобный буфер → [узел Q] фичи → 1D-CNN → годен/брак
                                                    │
                              MQTT: oee/line1/{state,count,verdict}
                                                    │
                              [oee-aggregator: A×P×Q → oee-dashboard (ratatui TUI)]
```

Состав репозитория (workspace):

- `line-simulator/` — генератор сценариев и сигналов; пишет сырые данные в CSV/бинарники
  (это же — датасет для обучения) и стримит в узлы.
- `nodes/` — узлы A/P/Q: приём данных, feature-extraction, `#[model]`-инференс, MQTT-публикация.
- `oee-aggregator/` — подписка на MQTT, формула OEE, публикация для дашборда.
- `oee-dashboard/` — TUI-дашборд (ratatui): live OEE/A/P/Q, счётчик, вердикты Q.
- `features-cli/` — **один и тот же Rust-код фич** для обучения (экспорт в Python) и для
  инференса: feature parity по построению, а не по гонке с numpy.
- `fork/microflow` — форк движка с `Conv1D` (git subtree или submodule).

## 4. Симулятор линии: что именно моделируем

- **Станок** — конечный автомат `idle → run → jam/overload` по сценарию; сценарий — декларативный
  список событий (t=120s: jam на 40s; t=600s: slowdown и т.д.), он же — ground truth.
- **Сигнал тока** — синтетический waveform: базовая синусоида 50 Гц + амплитудная огибающая по
  режиму + гармоники + шум (seeded RNG). Классы различимы, но не идеально — иначе ML бессмыслен.
- **Лента** — деталь проходит IR-барьер с джиттером; иногда две подряд (крайний случай:
  анти-двойной-счёт), иногда пропуск.
- **Tap-тест** — синтез звука: затухающая синусоида; целая деталь — высокая частота, долгое
  затухание; треснутая — ниже частота, быстрое затухание + шум. Параметры варьируются seeded RNG.
- **Воспроизводимость**: один seed → один и тот же датасет и эксперимент; в отчёте — таблица
  «сценарий → истинный OEE → измеренный OEE → ошибка».

## 5. Движковый вклад: `Conv1D` (локальный форк)

Нюанс недели 1 (spike): Keras `Conv1D` при экспорте в TFLite обычно сериализуется как `CONV_2D`
над тензором `(1, T, C)` с цепочкой `Reshape`. Поэтому работа:

1. Научить `microflow-macros` понимать эту цепочку и 3D-тензоры (flatbuffers-парсер).
2. Эффективный int8-кернел для 1D-случая: dot-product + int32-аккумулятор + requant.
3. Юнит-тесты против reference-модели (golden-вектора из Rust `golden-gen`, тот же тулчейн; numpy не используется — решение недели 1, спека §5.2).
4. Бенчмарк (criterion): «честный Conv1D vs reshape-трюк через Conv2D» — время, flash/RAM.

Вертикаль та же, что у автора движка: парсер → кодеген → рантайм → тесты. Без обязательств
перед апстримом: чистый эксперимент в форке + раздел бенчмарков в отчёте.

## 6. ML-конвейер (Python-сторона)

1. Датасеты генерирует `line-simulator` (те же CSV, что пойдут узлам на инференс).
2. Модели только из поддерживаемых операторов: `Conv1D(8)→AvgPool→Conv1D(16)→AvgPool→FC→Softmax`.
3. Квантизация full-integer int8 (post-training), экспорт `.tflite`.
4. Feature parity — главный источник боли в TinyML — здесь закрыт архитектурно: фичи для
   обучения и для инференса считает один Rust-крейт (`features-cli`); numpy получает уже
   готовые фичи. Golden-тесты остаются как страховка.

## 7. QEMU: «MCU без MCU»

- Целевая машина **LM3S6965** (`qemu-system-arm -M lm3s6965evb`) — официально протестирована
  автором MicroFlow и есть в stock QEMU, тулчейн `thumbv7m-none-eabi`.
- Прогон примеров и своих моделей через UART-вывод; метрики: flash/RAM из ELF (точно),
  латентность (приближённо — указать в ограничениях).
- Хост-бенчмарки criterion — основной источник чисел по скорости; QEMU — про переносимость
  и footprint.

## 8. Режим работы

- Одна тема на сессию: движок / ML / симулятор / интеграция — не смешивать.
- Порядок внутри темы: спека → код → тесты, а не «сразу написать Conv1D».
- Весь код проходит `cargo test` + `cargo clippy` — до перехода к следующей теме.

## 10. Метрики для отчёта (раздел «results»)

- **OEE-корректность**: серия сценариев (норма / простои / замедление / брак); таблица
  «истинный OEE → измеренный OEE → ошибка»; главный численный результат.
- **Движок**: латентность (min/avg/max) моделей на хосте и в QEMU, Δ flash/RAM,
  «Conv1D vs reshape-трюк» (criterion).
- **Узлы**: confusion matrix A и Q, PR-кривая порога брака, устойчивость к seed'ам.
- **Детерминизм**: один seed → идентичный повтор эксперимента (проверяется прогоном дважды).

## 11. Риски и их обработка

- **Сборка MicroFlow на хосте** (зависимости, Rust-версии) — риск №1 недели 1; если пример
  `sine` не собирается за вечер — ранний сигнал, перераспределить план сразу.
- **Парсер TFLite**: цепочка `Conv1D → Reshape → CONV_2D` может оказаться сложнее ожидаемого —
  именно поэтому spike вынесен на неделю 1, до написания кернела.
- **«Слишком хорошие» модели**: синтетика без реального шума даёт точность ~100% — лечится
  варьированием шума/параметров в симуляторе и анализом чувствительности в отчёте.
- **Тайминги QEMU не cycle-accurate** — честно указать в ограничениях; основные числа по
  скорости — хост-бенчмарки criterion.
- **Feature parity** — закрыт архитектурно (общий Rust-крейт фич), golden-тесты как страховка.
- **Вы — единственная точка отказа** — гейты «минимально готово», cut-line на неделю 4.
