## Д0 (вечер до старта, ~0.5 ч): входные условия

1. Ветка `feat/aggregator-dashboard`.
2. Перечитать `docs/week4-gate.md`: решение cut-line определяет Q-части дашборда и
   формулы (Quality = 1.0, если Q выброшен).
3. Свежий прогон стенда недели 4 — входные данные для разработки агрегатора.

## Д1 (пн, ~2–3 ч) — симулятор: лента; узел P: счёт

1. Лента в `line-simulator` (разд. 4): детали проходят IR-барьер; интервалы с
   джиттером, иногда две подряд (анти-двойной-счёт), иногда пропуск. События IR —
   в поток/CSV; ground truth — счёт по сценарию.
2. Узел P: детектор фронта + окно анти-двойного-счёта (два события внутри окна =
   одна деталь); P — событийный, без окон (`WindowSpec(P) = None`).
3. Публикация `oee/line1/p/count` (`{count, t_ms, run_id}`).

Проверка: на сценарии с двойными и пропусками счёт P = truth.

## Д2 (вт, ~2–3 ч) — агрегатор: MQTT + окна

1. Подписка `oee/line1/{a/status, p/count, q/verdict}`; окна агрегации: минута и
   смена (разд. 1).
2. Формулы на окне поверх готовой `oee()`: A = Run/Planned, P = IdealCycle×Count/RT,
   Q = Good/Total (или 1.0 по cut-line).
3. Публикация `oee/line1/oee` (JSON-схема — контракт дашборда Д3) + CSV-лог
   (сырьё для таблицы эксперимента).

Проверка: на ручном сценарии компоненты сходятся с truth по построению; юнит-тест
на фиксированном окне.

## Д3 (ср, ~3 ч) — TUI-дашборд на ratatui

Новый крейт `oee-dashboard` (6-я сущность workspace: корень + 5 крейтов), весь
стек на Rust. Слои:

| Слой                   | Что делает                                       | Тесты      |
| ---------------------- | ------------------------------------------------ | ---------- |
| MQTT-поток (rumqttc)   | подписка `oee/line1/#` → mpsc-канал              | реюз узлов |
| `DashboardState`       | чистая `on_message(topic, payload)` — вся логика | юнит-тесты |
| рендер `ui(f, &state)` | Gauge OEE/A/P/Q, счётчик, вердикты, Sparkline    | глазами    |

1. (0:00–0:20) каркас крейта, `ratatui::init()`, hello-world на экране.
2. (0:20–0:50) MQTT-поток (копипаста подписки из узла недели 4) + канал + статус-бар
   «обновлено N с назад» (замечает обрыв брокера).
3. (0:50–1:40) `on_message`: JSON `oee/line1/oee` (схема из Д2), цвета зон
   (зелёный ≥85%, жёлтый ≥60% — ориентиры разд. 1), счётчик P, лента вердиктов Q;
   юнит-тест на битый payload — мусор не роняет витрину (error isolation).
4. (1:40–2:10) Sparkline истории OEE; перерисовка ~5 fps, `q` — выход;
   `ratatui::restore()` по panic hook.
5. (2:10–3:00) полный прогон со стендом, узкий терминал, буфер.

Таблица «measured vs truth» — из CSV агрегатора, в TUI не тащим.

Проверка: при прогоне симулятора цифры живут и меняются; `cargo test` крейта
зелёный.

Запасной план: ratatui буксует дольше ~1,5 ч → Node-RED в контейнере (виджеты без
кода); минимальный fallback — MQTTX (~15 мин, живой просмотр топиков). На гейт не
влияет: главный артефакт недели — таблица, а не витрина.

## Д4 (чт, ~3–4 ч) — главный эксперимент

1. Сценарии по разд. 10: норма / простои / замедление / брак; каждый — свой seed.
   Замедление — лента медленнее номинала (P < 1); брак — тапы треснутые (Q < 1),
   если Q жив.
2. Автосбор: прогон → CSV агрегатора → таблица «истинный OEE → измеренный →
   ошибка»; истинный считается из сценария (ground truth по построению).
3. Прогон дважды одним seed — идентичный результат (детерминизм, разд. 10).

Проверка: таблица заполнена по всем четырём сценариям.

## Точки эскалации

- Измеренный OEE сильно ≠ истинный → сверять по компонентам (A, P, Q отдельно):
  чаще всего виноваты окно анти-счёта P или окна A — там и править.
- ratatui буксует → запасной план Node-RED / MQTTX (см. Д3); гейт не блокируется.
- Сценарии дают «идеальные» 0% ошибки → ужесточить шум/джиттер, иначе таблица
  неубедительна (риск «слишком хорошо», разд. 11).
- Агрегатор тонет в состояниях окон → упростить до одного окна (минута), смену
  считать постфактум из CSV; живым оставить только минутное.
