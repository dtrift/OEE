## Этап 0 — инструменты (один раз, ~30 мин на чистой машине)

Те же, что для узлов A/Q (общий тулчейн стенда):

```bash
cargo install espup espflash
espup install                    # пропатченный Xtensa-тулчейн → ~/.rustup/toolchains/esp
. $HOME/export-esp.sh            # PATH линкера (xtensa-esp-elf-gcc)
asdf reshim rust                 # если asdf-руст: бинарники упали в ~/.asdf/.../bin
sudo usermod -aG dialout $USER   # права на порт; в текущем шелле — newgrp dialout
```

Грабля из NOTES: тулчейн esp стоит в `~/.rustup/toolchains/esp`, который
asdf-шелловый rustup не видит — cargo возьмёт шелловый stable и упадёт на
`-Z`-флагах. Поэтому перед каждой целевой сборкой:

```bash
export PATH="$HOME/.rustup/toolchains/esp/bin:$PATH"
```

Чек: `espflash --version` ≥ 4.6 (младшие отказываются шить образ с
дескриптором ESP-IDF, который уже вшит в прошивку).

## Этап 1 — хост-проверки логики (~10 мин, без железа)

```bash
cd firmware && cargo test --workspace
```

Что именно закреплено тестами и важно для P: логика `EdgeCounter`
(антидребезг 50 мс — `DEBOUNCE_MS`, нарастающий фронт, шторм глитчей не
замораживает счётчик) и формат строки `format_count`
(`p,bench-p,777,131\n` — тест в lib). Красные тесты — стоп, дальше идти
бессмысленно.

## Этап 2 — сборка release-образа (~10 мин)

```bash
cd firmware
export PATH="$HOME/.rustup/toolchains/esp/bin:$PATH"
. $HOME/export-esp.sh
cargo build --release -p firmware-p --target xtensa-esp32s3-none-elf
```

Артефакт: `firmware/target/xtensa-esp32s3-none-elf/release/firmware-p`
(один ELF; espflash сам превращает его в загрузочный образ — отдельный .bin
не нужен). Release, не debug: паники печатаются в UART и так. НЕ прошивать
`qemu/target/.../oee-qemu` — другая цель (LM3S6965/Cortex-M3).

## Этап 3 — монтаж TCRT5000 и настройка порога (~1 ч)

По `docs/rus/bench-assembly.md`: разд. 3а (общий план), 6 (распиновка),
6а (схема рядов и настройка). Плата — НЕ в макетке, лежит рядом; модуль —
на макетке, соединения джамперами M-F.

**Обязательная проверка ДО монтажа** (runbook, шаг 6): узел P живёт на
CAM-плате, датчик назначен на GPIO5 (`board::node_p::IR_OUT`), но обвязка
камеры OV2640 на платах разных производителей занимает разные пины, и на
части плат GPIO5 принадлежит камере. Сверить распиновку вашей платы со
схемой. Если GPIO5 занят — датчик переносится на свободный пин, а правка
делается в крейте `board` (уровень конфигурации стенда; контракт узла не
меняется). Тест `used_pins_are_free_and_distinct` проверит, что новый пин
не входит в зарезервированный список: 0, 3, 45, 46 (пины режимов загрузки),
19, 20 (линии USB), 43, 44 (консоль UART0), 35, 36, 37 (линии восьмиразрядной
PSRAM модуля N16R8).

Модуль TCRT5000 (3–4 пина: VCC, GND, OUT, у некоторых + A0) — в ряды 30–32
поперёк желоба; используется только цифровой OUT:

| Вывод | Куда                                                     |
| ----- | -------------------------------------------------------- |
| VCC   | 3.3 В (по маркировке модуля; есть модули на 5 В)         |
| GND   | шина (−)                                                 |
| OUT   | GPIO5 платы CAM (или выбранный свободный пин — см. выше) |
| A0    | не используется                                          |

Датчик рефлективный инфракрасный: срабатывает на отражение на расстоянии
~1–25 мм, порог подстраивается многооборотным резистором на модуле.

Установка на ленте: излучатель/приёмник смотрят ПОПЕРЁК хода — в щель между
лентой и сходом (или через щель в направляющей); расстояние до проходящей
детали 2–10 мм; крепление — кронштейн из шпажки/струбцина, чтобы не сместить
при касании.

Настройка подстроечника (на модуле многооборотный резистор + два LED):

1. Лента пустая, питание подано: крутить до устойчивого LED «обнаружение
   ВЫКЛ» (OUT в состоянии «пусто» — для нашей разводки низкий уровень).
2. Пронести гайку мимо зазора: LED «обнаружение» мигает на каждый проход.
3. LED горит постоянно (видит ленту/направляющую) — увеличить расстояние
   или прикрыть боковое окно излучателя картонкой от переотражений.
4. Не реагирует — уменьшить расстояние/прижать.

Чек перед подключением к плате: тестером уровень OUT модуля в покое и при
срабатывании (поднести палец/гайку) — записать полярность. Прошивка считает
НАРАСТАЮЩИЙ фронт (деталь вошла в зазор, подтяжка входа — вниз); если модуль
даёт инверсию (OUT высокий в пустоте) — правка в `firmware-p/src/main.rs`
(место помечено комментарием), а не в счётчике.

## Этап 4 — прошивка и smoke-проверка проводком (~20 мин)

Из каталога `firmware/` (путь к артефакту — `target/...`; из корня репо —
`firmware/target/...`):

```bash
espflash flash -M --port /dev/serial/by-id/usb-1a86_USB_Single_Serial_5CCC048683-if00 \
    target/xtensa-esp32s3-none-elf/release/firmware-p
# -M = заливка и сразу монитор; отдельный монитор (если плата уже прошита):
# espflash monitor --port /dev/serial/by-id/usb-1a86_USB_Single_Serial_5CCC048683-if00
```

Грабля из NOTES (поймана на этой плате 2026-09-14): прошивать и мониторить —
только через мостовой порт «COM» (by-id `usb-1a86_*`). Нативный «USB»-порт
CAM-платы (Espressif `303a:4001`) даёт «Failed to connect» — авто-вход в
download-режим не срабатывает. Если и мост не видит плату — зажать BOOT при
подключении.

Ожидание в мониторе (115200):

```text
p: boot, run_id=bench-p
...тишина — норма: у P нет периодики, только события
```

Проверка реагирования проводком (runbook, шаг 0.5): проводником замкнуть
GPIO5 на 3V3 — держать не меньше 60 мс, отпустить, повторить. Антидребезг
50 мс игнорирует замыкания короче 50 мс, поэтому каждое корректное касание
даёт ровно один инкремент:

```text
p,bench-p,1200,1
p,bench-p,3100,2
...
```

Если счётчик растёт от коротких касаний (меньше 50 мс) — константа
`DEBOUNCE_MS` в прошивке не соответствует фактическому параметру: это
находка для NOTES, а не для молчаливой правки.

## Этап 5 — S6: счёт деталей на ленте (~2 ч)

Цель: счётчик равен факту — N прошедших деталей дают ровно N инкрементов,
дребезг на краю датчика не создаёт ложных. Детали — runbook, шаг 6.

Действия:

1. Подстроить расстояние: деталь на 5–10 мм от датчика — светодиод модуля
   загорается.
2. Повторить быструю проверку проводком из этапа 4 (каждое касание длиннее
   60 мс — ровно один инкремент).
3. Прогон 1: 20 медленных проходов детали (или пальца) — итоговый счёт
   ровно 20.
4. Прогон 2: 20 проходов в темпе будущей ленты.
5. Тест дребезга: держать цель на краю срабатывания и шевелить её пять
   секунд.

Критерии пройдено: в обоих прогонах расхождение счёта с фактом — ноль; тест
дребезга даёт не больше двух лишних инкрементов за пять секунд (антидребезг
50 мс подавляет серии короче 50 мс; устойчивые повторные пересечения порога
длиннее 50 мс — это уже реальные события).

Сценарии неудач: счёт вдвое больше факта — сигнал во время прохода уходит
за порог и возвращается (видно на записи уровня OUT): увеличить зазор
датчика или уменьшить чувствительность резистором. Счёт ноль, хотя
светодиод модуля срабатывает, — у модуля инвертированный выход (активный
низкий уровень): проверить тестером уровень OUT в покое и при срабатывании;
при инверсии правка делается в драйвере чтения пина в прошивке (не в
контракте) и фиксируется в NOTES.

Записать в `firmware/NOTES.md`: полярность срабатывания, дистанцию, итоги
обоих прогонов, результат теста дребезга.

Если по итогам менялись пин (GPIO5 занят камерой) или инверсия уровня —
перевыпустить образы в `firmware/bin/` по процедуре 2026-09-14: новая метка
времени, sha256, build-info.md; старый сет — в `tmp/trash/`.

## Этап 6 — включение в цикл OEE (~30 мин, после гейта)

Агрегатор — из ветки `firmware-a` (там фикс: ping каждые 15 с, строго внутри
30-секундного idle-cut брокера; в `main` его ещё нет). Команды — из корня
репо:

```bash
./target/debug/broker 1883 &
./target/debug/aggregator --mqtt 127.0.0.1:1883 --ideal-cycle-ms 400 --out windows.csv --expect a,p
./target/debug/oee-dashboard --mqtt 127.0.0.1:1883
```

Отдельный терминал — строки платы в MQTT:

```bash
cat /dev/serial/by-id/usb-1a86_USB_Single_Serial_5CCC048683-if00 | \
    cargo run -p firmware-tools --bin uart-bridge -- 127.0.0.1:1883
```

Гейджи P на дашборде оживают на каждую деталь; boot-строку мост отфильтрует
(закреплено его тестами). Живая проверка моста без платы:

```bash
printf 'p: boot, run_id=bench-p\np,bench-p,3000,1\n' | \
    cargo run -p firmware-tools --bin uart-bridge -- 127.0.0.1:1883
```

## Критерии готовности узла P (локальный гейт S6)

- [ ] GPIO5 сверен со схемой CAM-платы (свободен от камеры) либо пин перенесён
      с тестом `used_pins_are_free_and_distinct`.
- [ ] Проводок: каждое касание ≥60 мс — ровно один инкремент; касания <50 мс
      счёт не растят.
- [ ] Прогон 1: 20 медленных проходов — счёт ровно 20.
- [ ] Прогон 2: 20 проходов в темпе ленты — счёт ровно 20.
- [ ] Тест дребезга: не больше двух лишних инкрементов за 5 с.
- [ ] Полярность OUT и рабочая дистанция записаны в NOTES.
- [ ] Если правились пин или инверсия — образ перевыпущен в `firmware/bin/`
      (метка, sha256, build-info), старый сет в `tmp/trash/`.

## Безопасность

- Перед любым перемонтажом — отключить USB платы.
- Датчик слаботочный (3.3/5 В по маркировке модуля); сеть 220 В для монтажа
  недоступна.
- У P нет актуаторов — это самый простой из трёх узлов: риска серво-питания
  и тап-позиции здесь нет.

### Грабля с именем порта (закрыта 2026-09-17)

Симптом: `Error while connecting to device — No such file or directory` на
этапе подключения (до чтения ELF). Причина: короткая форма
`usb-1a86_USB_Serial_<SN>-if00` (шапка runbook) на этом стенде не
существует; наблюдаемое имя строится из строки продукта моста
`USB Single Serial`:

```text
/dev/serial/by-id/usb-1a86_USB_Single_Serial_5CCC048683-if00
```

Диагностика (порядок шагов): `lsusb` → мост `1a86:55d3 QinHeng "USB Single
Serial"` виден; `/sys/class/tty/ttyACM0` существует (ядро создало порт);
продуктовая строка → by-id-имя. Правильная форма зафиксирована в
`firmware/README.ru.md` (коммит 5d9d370); расхождение с runbook — кандидат
на правку репо-дока.

Попутная грабля: первая попытка шла из каталога `firmware/` с путём
`firmware/target/...` (двойное `firmware/`) — из `firmware/` путь
`target/...`, из корня репо — `firmware/target/...`; ошибка порта маскировала
её до поры.

WARN espflash «Monitor options were provided...» — безвреден: monitor-опции
из пользовательского конфигурационного файла игнорируются без флага `-M`.

### Интерпретация счётных строк

Каждая строка — один принятый фронт на GPIO5 (высокий уровень ≥50 мс,
антидребезг), `t_ms` — от старта; 16 событий за ~98 с. Развилка:

- каденс (пара касаний → пауза ~37 с → серия) похож на ручную проверку
  проводком GPIO5 → 3V3 — тогда этап 4 закрыт: ровно +1 на касание, дребезг
  съедается, формат строки верен;
- если касаний не было — спонтанные фронты. Интервалы 1–3 с исключают
  сетевую наводку (50 Гц давала бы десятки событий в секунду); вероятный
  источник — порог TCRT5000 (рука/предмет/ИК-фон на грани срабатывания).

Проверка «пусто» (обязательна до S6):

1. Убрать всё из поля зрения датчика и не двигаться 30 с — счёт должен
   замереть.
2. LED модуля мигает синхронно со строками → реально срабатывает датчик
   (настройка подстроечником, этап 3); LED молчит, а строки идут → шум по
