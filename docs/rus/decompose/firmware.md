# Колея железа — декомпозиция (прошивки ESP32-S3, обкатка на стенде)

> Ветка: `feat/firmware-bringup` (только `firmware/` workspace + CI; при баге
> инференса — hotfix-ветка форка, как в неделе 4).

> Разложение трека «колея железа» из плана [`plan.md`](../plan.md), разд. 2 и 12.
> Трек вне календаря недель 1–6: идёт параллельно, критический путь курса его не
> ждёт (правило разд. 2). Формат — сессии по ~2–3 ч (одна тема на сессию,
> правило разд. 8), оценка ~20–24 ч. Стенд: 2× ESP32-S3-DevKitC-1 (N16R8) —
> узлы A и Q; 1× ESP32-S3-WROOM-1 N16R8 CAM с OV2640 на борту — узел P и
> stretch-камера; сенсоры ACS712-20A, INMP441, TCRT5000, серво-таппер,
> отдельный БП 5 В. Подробности стенда и процедура оживления —
> [`firmware/README.md`](../../../firmware/README.md).

> Вход: контракты уже в репо — `features-cli` (`window_spec`, калибровка
> ADC→амперы, схема `capture`), `nodes::source::SensorSource`
> (`AdcSource`/`I2sSource`/`GpioEdgeSource`), `board` (пины стенда + тест),
> скелеты `firmware-{a,q,p}` (собираются на хосте без тулчейна), rust-born
> модели `model_a.tflite`/`model_q.tflite` (`#[model]`, no_std) и хостовые
> пайплайны недель 4 (`nodes` — эталон поведения). QEMU-демо недели 6 —
> отдельная линия (другой таргет), с этой колеёй не смешивается.

## Гейт колеи (минимально готово)

- [ ] `firmware-a` на бенч-прогоне: статусы совпадают с хостовым узлом A на
      тех же данных (расхождения — только на границах окон, как в неделе 4).
- [ ] `firmware-q`: вердикты на эталонных деталях (годная/треснутая) совпадают
      с моделью на хосте на тех же окнах.
- [ ] `firmware-p`: счёт деталей равен факту прогона; дребезг погашен.
- [ ] Capture-CSV с платы читается хостовыми тулзами (конвертер capture→run
      + узел A); захваты воспроизводимы.
- [ ] CI: третий job build-only под `xtensa-esp32s3-none-elf` зелёный.
- [ ] `firmware/NOTES.md` с фактами обкатки; решение по фазе 2 (UART-мост vs
      Wi-Fi) зафиксировано в [firmware-gate.md](../firmware-gate.md).

## Сводка по сессиям

| Этап | Тема сессии | Суть                                         | Артефакт                      |
| ---- | ----------- | -------------------------------------------- | ----------------------------- |
| Э0   | тулчейн     | espup, blinky, CI build-only                 | blinky на плате, зелёный job  |
| Э1   | узел A      | ADC1 + ACS712, калибровка, capture по UART   | capture-CSV, ноль в допуске   |
| Э2   | узел A      | окно → `#[model]` → гистерезис → статус      | статусы A в UART              |
| Э3   | сверка      | тот же прогон: плата vs хостовый узел A      | таблица расхождений в NOTES   |
| Э4   | узел Q      | I2S INMP441, окно 1024, дамп спектра         | окно с тоном в нужном бине    |
| Э5   | узел Q      | серво-таппер, `#[model] model_q`, вердикты   | вердикты на эталонных деталях |
| Э6   | узел P      | TCRT5000, анти-дребезг 50 мс, счёт           | счёт = факт прогона           |
| Э7   | гейт        | NOTES обкатки, firmware-gate, решение фазы 2 | `docs/firmware-gate.md`       |

## Э0 (~2 ч) — тулчейн: espup, blinky, CI

1. `espup install` + `rustup component add rust-src` + `. $HOME/export-esp.sh`
   (шаги 1–3 «оживления» из firmware/README).
2. В `firmware-a` раскомментировать зависимости (`board`, `features-cli`,
   `esp-hal 1.1.2`) — шаг 4; blinky на пине из `board` (плата жива, пины
   сходятся со схемой).
3. CI: третий job build-only `cargo build -p firmware-a --target
   xtensa-esp32s3-none-elf` (без тестов — правило README: на железе проверяет
   человек; юнит-тесты остаются у чистой логики, прецедент — `board`).

Проверка: blinky мигает; CI-джоба зелёная в PR.

## Э1 (~3 ч) — узел A: АЦП и калибровка

1. `AdcSource`: реализация `SensorSource` поверх ADC1 (ACS712), выборка с
   темпом ≥ `window_spec(A).sample_rate_hz` (1.6 кГц, таймер); пины — из
   `board`.
2. Стартовая рекалибровка нуля: усреднение покоя →
   `CurrentCalibration::with_zero_counts` (дрейф нуля ACS712 — ожидаемый факт,
   контракт уже готов).
3. Захват: строки capture-CSV (`t_ms,node,run_id,value,state,note`) по UART;
   хостовым терминалом пишется в файл.

Проверка: покой ≈ 0 А (в допуске калибровки); мультиметр vs показания
линейны на 2–3 номиналах тока.

## Э2 (~3 ч) — узел A: окно → predict → статус

1. Подключить форк из firmware-workspace: path-зависимость
   `../fork/microflow` + продублированный `[patch.crates-io] nalgebra` в
   `firmware/Cargo.toml` (конвенция корневого манифеста, неделя 3/Д6).
2. Окно `WindowSpec(A)` = 128 @ 1.6 кГц → `#[model("ml/models/model_a.tflite")]`
   → гистерезис ×2. Логика окна/гистерезиса — компактная копия из
   `nodes::status` (~50 строк, `no_std` + alloc) с хостовым юнит-тестом
   эквивалентности; выделение общего крейта — только по эскалации.
3. Статус в UART строкой `a,<run_id>,<t_ms>,<state>` (семейство offline-CSV
   недели 4) — по подтверждённому изменению, не каждым окном.

Проверка: на штатных режимах стенда статусы меняются по режиму; расхождения —
только на границах (аналог проверки Д1 недели 4).

## Э3 (~2 ч) — сверка двойника и железа

1. Конвертер capture→run CSV на хосте (маленькая утилита: переименование
   колонок `value→current_a`, фильтр `node=a`) — железные захваты становятся
   входом хостового `node --kind a`.
2. Один и тот же физический прогон: захват с платы → capture-CSV → хостовый
   узел; таблица расхождений статусов → `firmware/NOTES.md`.

Проверка: статусы совпадают вне границ окон; иначе — фикс (калибровка/порог),
причина и решение в NOTES.

## Э4 (~3 ч) — узел Q: I2S-микрофон

1. `I2sSource`: INMP441, 16 кГц (`window_spec(Q)`), DMA-кольцо; фреймы → f32
   с фиксируемой нормировкой.
2. Дамп окна 1024 по UART по команде; спектр на хосте (серийные инструменты).

Проверка: тон известной частоты (генератор/приложение) попадает в ожидаемый
бин ±5%; окно ровно 64 мс.

## Э5 (~3 ч) — узел Q: таппер и вердикты

1. Серво: PWM-импульс удара; синхронизация «тап → запись 64 мс» (окно
   начинается с удара, как в симуляторе `taps.rs`).
2. `#[model("ml/models/model_q.tflite")]` → вердикт в UART
   (`q,<run_id>,<t_ms>,verdict`).
3. Питание серво — строго отдельный БП 5 В + 470 мкФ у ножек (условие из
   firmware/README: просадка перезагружает плату).

Проверка: эталонные детали (≥5 годных, ≥5 треснутых) — вердикты совпадают с
классом детали; расхождения — в NOTES.

## Э6 (~2 ч) — узел P: счёт деталей

1. `GpioEdgeSource`: TCRT5000, фронт прохождения детали + анти-дребезг 50 мс
   (параметр из firmware/README), счётчик. Узел P живёт на плате CAM
   (ESP32-S3 WROOM N16R8 CAM): пин выбрать свободным от камеры и
   зарезервированных (раскладку камеры своей платы сверить по её схеме —
   разводка CAM-плат различается).
2. Счёт по изменению в UART (`p,<run_id>,<t_ms>,count`).

Проверка: прогон N деталей → счёт = N; дребезг/повторы не дают ложных срабатываний.

## Э7 (~2–3 ч) — гейт и NOTES

1. `firmware/NOTES.md`: факты обкатки (каденция и шум АЦП, смещение нуля,
   порядок байт/каналов I2S, ток серво, дребезг P).
2. Гейт-док [firmware-gate.md](../firmware-gate.md) (rus/eng, по образцу
   гейтов недель): чеклист, отступления, ретро.
3. Решение по фазе 2: UART-мост хоста → mosquitto (быстрый путь, стенд
   в полном контуре с агрегатором недели 5) vs `esp-wifi` + порт `mqtt-min`
   (future work).

## Точки эскалации

- Тулчейн espup не собирается / плата не прошивается → колея сдвигается
  целиком: контракты уже зафиксированы (страховка недели 1), курс это не
  блокирует; вернуться после недели 6.
- Шум АЦП выше ожидаемого → стартовая рекалибровка + усреднение; далее —
  аппаратный RC-фильтр (правка в схеме/`board`, не в контрактах).
- I2S приходит не тем порядком/энддианом → дамп сырого окна, сверка с
  эталоном, фикс локально в `I2sSource`; контракт `SensorSource` не меняется.
- Модель на плате расходится с хостом больше ±1 кванта → hotfix-ветка форка
  (прецедент — неделя 3) + вопрос: почему не поймал parity-тест; дыру закрыть
  тестом.
- Серво роняет питание → это аппаратная проблема (отдельный БП, 470 мкФ),
  софтверно не лечится.
- Срочно нужен MQTT со стенда → UART-мост хостом (публикация `oee/line1/*`
  из статусных строк); портирование `mqtt-min` на no_std — future work.

## Анти-скоп (чего НЕ делаем в этой колее)

- Агрегатор и дашборд на плату не переносим — они хостовые (недели 5–6).
- OTA, хранение истории на плате, конфигурация по сети — нет.
- Обучение/PTQ на плате — нет; модели рождаются в `ml/` и запекаются `#[model]`.
- Изменение контрактов `features-cli` ради железа — только отдельным
  решением, с сохранением хостовых потребителей.
- QEMU-линию недели 6 (`thumbv7m`) сюда не смешиваем: другой таргет,
  другой артефакт.

## Фаза 2 (после гейта, отдельным решением)

- UART-мост: хостовая утилита читает статусные строки плат A/P/Q и
  публикует в `mosquitto` на `oee/line1/*` — стенд входит в полный контур
  цифрового двойника (агрегатор/дашборд недели 5) без единой строки
  сетевого кода на платах.
- `esp-wifi` + портирование `mqtt-min` (SUBSCRIBE агрегатора тоже) —
  кандидат в future work отчёта.
