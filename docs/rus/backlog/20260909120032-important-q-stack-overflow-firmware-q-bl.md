# Вероятный stack overflow main-задачи ESP32 в node Q

- **Серьёзность**: важно
- **Компонент**: firmware-q
- **Источник**: ревью `backlog/20260909120000-review.md`, приложение А6, «Важно» №4
- **Локация**: `firmware/q/src/main.rs:99` + `firmware/q/src/lib.rs:31-45`; оценка буферов — `ml/models/model_q.ops.txt`

## Суть

Окно `[f32; 1024]` = 4 КиБ на стеке; в `classify` оно копируется в `SMatrix` (ещё 4 КиБ); `predict` для model_q требует int8-буферы слоёв:

- `conv0_out` 1022×8 = 8176 Б;
- `conv2_out` 509×16 = 8144 Б;
- `pool1`/`pool3` ещё ~8 КиБ.

Пиковое потребление правдоподобно 12–20+ КиБ при дефолтном стеке main-задачи esp-hal. CI-job `firmware` — build-only и этого не поймает: узнаете на железе зависанием.

Для узла A (128×4 = 512 Б) запас есть.

## Предлагаемое исправление

- Поднять размер стека main-задачи через `esp_hal::Config` (точное имя метода проверить по версии esp-hal);
- и/или сделать окно `static` (`StaticCell`/`static mut` с обоснованием);
- проверить высокую воду при bring-up, до перехода на реальный I2S (DMA-буферы добавятся сверху).
