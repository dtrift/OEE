# Flaky-тест `aggregator_subscribes_folds_publishes_and_flushes_on_end_markers`

- **Серьёзность**: важно
- **Компонент**: oee-aggregator
- **Источник**: локальный прогон всех CI-проверок 2026-09-10 (не из код-ревью — найдено при верификации)
- **Локация**: `oee-aggregator/tests/aggregator_pipeline.rs:32-147`; брокер: `mqtt-min/src/testing.rs` (`LoopbackBroker::spawn` → `bind("127.0.0.1:0")`)

## Симптом

При `cargo test --workspace` (параллельный прогон сюит) тест упал **1 раз из 4 запусков** (~25%):

- упавший прогон: длительность теста **0.04 с** — мгновенная ошибка, не таймаут (в тесте таймауты 5 с на `next_oee`/`recv_timeout` и дедлайн 30 с);
- изолированный прогон `cargo test -p oee-aggregator --test aggregator_pipeline` — стабильно зелёный;
- 3 последующих полных `cargo test --workspace` — зелёные (0 фейлов).

Точное panic-сообщение **не зафиксировано** — вывод первого прогона фильтровался grep'ом по `test result`. Это первый шаг диагностики (ниже).

## Repro

```bash
cd /home/timur/projects/OEE

# изолированно — ожидается стабильно зелёный (контроль):
cargo test -p oee-aggregator --test aggregator_pipeline

# полный параллельный прогон циклом — ловим фейл с ПОЛНЫМ выводом:
for i in $(seq 1 20); do
  echo "== run $i";
  cargo test --workspace 2>&1 | tee /tmp/ws-test-$i.log | grep -E "FAILED|panicked";
done

# проверка гипотезы параллелизма (последовательные сюиты):
cargo test --workspace -- --test-threads=1
```

Ожидание: фейлы только в параллельном режиме; в `/tmp/ws-test-*.log` у упавшего прогона виден полный panic (строка теста + причина).

## Что уже исключено

- **Конфликт портов между сюитами**: `LoopbackBroker::spawn` биндит эпемеральный порт (`127.0.0.1:0`) — параллельные сюиты mqtt-min/aggregator портов не делят.
- **Влияние недавних правок** (план 20260910095045 и дозакрытие 07/31/47): агрегатор и его тесты не менялись; фейл воспроизводится на коде, который был зелёным в CI до этого.

## Гипотезы (по убыванию правдоподобия)

1. **Гонка потоков на wire-пути под нагрузкой**: тест создаёт 5 соединений (dashboard, агрегатор, 3 ноды) к брокеру с потоком на соединение; при параллельной загрузке машины тестовыми потоками других крейтов вероятны мгновенные `Err` на `Client::connect(...).unwrap()` / `subscribe(...).unwrap()` / `next_message` (reset соединения reader-потоком брокера).
2. **Регистрация подписки vs публикация**: `ready`-барьер закрывает гонку подписки агрегатора, но подписка `dashboard` на `oee/line1/#` не барьерится ничем — если reader-поток брокера не успел зарегистрировать её до... (менее вероятно: подписка делается до старта нод).
3. **Утечка/сбой reader-потока LoopbackBroker** под параллельной нагрузкой (очередь capture-канала, паника в потоке соединения).

## Предлагаемое исправление

1. Зафиксировать panic упавшего прогона (repro выше) — до этого фикс вслепую не делать.
2. В зависимости от строки падения:
   - `connect`/`subscribe` в тесте — заменить `.unwrap()` на retry с bounded backoff (мелкий хелпер), как это уже сделано в `MqttSink` нод;
   - гонка в брокере/клиенте — фиксить в `mqtt-min` (смежной кандидатской точкой является reader-поток `testing.rs`);
3. Если корень — машинная нагрузка CI: рассмотреть `#[ignore]`… нет — правильно: сделать тест устойчивым (retry), а не игнорировать: это единственный e2e-тест wire-пути рантайма агрегатора.
