Сводный список мелких замечаний:

1. `a.rs:56`, `q.rs:43` — `partial_cmp(b).unwrap()` паникует на NaN. Заменить на `f32::total_cmp`: `max_by(|(_, a), (_, b)| a.total_cmp(b))`.
2. `sim_source.rs:94` — `record.get(2)?.to_string()` + замена `last_state` — аллокация String **на каждую строку** (~96 тыс. на 60-секундный прогон) для поля «diagnostics only». Убрать или не хранить (парсить только `t_ms`/`current_a`).
3. `status.rs:132` — `mem::take` оставляет Vec с capacity 0 → ~7 реаллокаций на каждое окно. Пул из двух буферов (swap со spare) уберёт аллокации в горячем цикле; для firmware-трека будет заметно.
4. DRY между A и Q: argmax продублирован (`a.rs:53-58` / `q.rs:40-46`), `RunSummary`+цикл похожи; три ветки MQTT-обвязки в `bin/node.rs:71-175` — почти копии (meta → run → end → println). Вынести общий helper.
5. `mqtt_sink.rs:149-173` — диспетчер по строкам с `else` → топик Q: строка с опечаткой в `node` молча уедет в `q/verdict`. Явный match по `NodeKind` или `debug_assert!` на else-ветку.
6. `status.rs:4-6` — doc заявляет «follows the capture schema family (`features_cli::capture`)», но фактическая схема `node,run_id,t_ms,state` ≠ `CAPTURE_HEADER = [t_ms,node,run_id,value,state,note]` (`capture.rs:10`). Смягчить формулировку или свести схемы.
7. `a.rs:102`, `q.rs:69`, `p.rs:122` — `while let Ok(...)` молча завершает прогон и по `SourceError::Sensor` (не только `Exhausted`), после чего публикуется штатный end-marker — агрегатор не отличит обрыв от конца. Различить ветки хотя бы логом/счётчиком.
8. `examples/qemu_host_ref.rs:28` — `STATE_NAMES[argmax]` без clamp (в отличие от `a.rs:117`); недостижимо, но непоследовательно.
9. `lib.rs:31-39` — тест `skeleton_imports` ничего не гарантирует, кроме компиляции модулей; удалить или оставить осознанно.
