# Десинхронизация потока при mid-packet таймауте

- **Серьёзность**: критично
- **Компонент**: mqtt-min
- **Источник**: ревью `backlog/20260909120000-review.md`, приложение А4, «Критично» №1
- **Локация**: `mqtt-min/src/lib.rs:212-272` (`read_remaining_length_retry`, `read_exact_retry`); инвариант задекларирован в `lib.rs:139-142`

## Суть

`read_remaining_length_retry` вызывает `read_remaining_length` с нуля: если первая попытка успела потребить старший байт varint (например, `0xC0`) и упала по таймауту на втором байте, retry прочтёт *следующий* байт потока как первый байт varint. Аналогично `read_exact_retry`: `read_exact` при таймауте уже частично заполнил `body` (байты потреблены из сокета), а retry перезаполняет буфер с индекса 0 — начало тела теряется, «хвост» следующего пакета съедается.

Комментарий `lib.rs:139-142` («the stream cannot desync») декларирует ровно противоположное.

Триггер: сегментация TCP с задержкой между частями пакета больше таймаута вызова (500 мс у дашборда). На localhost практически не встречается, на сети — реально. Последствие — тихая порча кадра вместо чистой ошибки. Буферизации до полного пакета сейчас нет.

## Предлагаемое исправление

Либо:

- resumable-чтение: курсор по varint/буферу, таймаут лишь продлевает ожидание при фиксированном общем дедлайне;
- либо минимально: считать mid-packet timeout фатальной ошибкой соединения (как уже делает `read_packet`), а не рестартовать разбор.

## Тесты

Тест на сборку пакета из фрагментов TCP: фейк-брокер пишет по байтам с паузами (прикрыл бы этот баг).
