# End-marker публикуется без ретрая и не на всех путях выхода

- **Серьёзность**: важно
- **Компонент**: nodes
- **Источник**: ревью `backlog/20260909120000-review.md`, приложение А2, «Важно» №1
- **Локация**: `nodes/src/bin/node.rs:89, 121, 157`; смежное: `nodes/src/mqtt_sink.rs:139-142`, `a.rs:56`, `q.rs:43`

## Суть

- Если нода запаникует до `publish_end` (например, `partial_cmp().unwrap()` в `a.rs:56`/`q.rs:43` при NaN, или kill процесса), маркер `{node}/end` не выйдет никогда — агрегатор, ожидающий конца от всех нод, повиснет.
- Даже при штатном завершении `publish_end` — **одна попытка**: если брокер в этот момент недоступен (сценарий деградации D5), маркер молча теряется (возвращаемый `bool` игнорируется).
- Аналогично игнорируются результаты `publish_{a,p,q}_meta` (строки 83, 118, 154): брокер недоступен на старте → meta потеряна навсегда, хотя статусы потом переподключатся.

Парная карточка на стороне агрегатора: `20260909120002-critical-hang-on-lost-end-marker-oee-aggregator-bl.md` (таймаут/дедлайн).

## Предлагаемое исправление

- Ретраить `publish_end` с capped backoff N раз (это flush-сигнал, он важнее обычных статусов).
- Как минимум логировать/учитывать неудачу meta-публикаций.
- `catch_unwind` вокруг `run_*` с публикацией end перед re-panic.

## Тесты

- End-marker для A и Q (сейчас покрыт только P: `node_p_publishes_counts_over_mqtt`; `both_nodes_one_run_with_mqtt` не публикует ни meta, ни end).
- Реконнект `MqttSink` при падении брокера между publish'ами (сейчас тестируется только мёртвый брокер).
