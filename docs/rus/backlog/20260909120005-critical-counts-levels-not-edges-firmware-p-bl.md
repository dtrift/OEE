# Node P (прошивка): счёт уровней вместо фронтов — overcount деталей

- **Серьёзность**: критично
- **Компонент**: firmware-p
- **Источник**: ревью `backlog/20260909120000-review.md`, приложение А6, «Критично» №1
- **Локация**: `firmware/p/src/lib.rs:35-50`; host-эталон: `nodes/src/p.rs`

## Суть

`observe(level=true)` засчитывает деталь при *каждом* опросе вне 50-мс окна: `!level → return`, но внутри нет проверки перехода low→high. Пин, удерживаемый высоким дольше 50 мс (реальная деталь в зазоре барьера — десятки/сотни мс при такте подачи 400 мс), даёт повторный счёт каждые ~51 мс. Даже собственный чек из `firmware/README.md` («jumper GPIO5 → 3V3, hold ≥ 60 ms») даст двойной счёт.

Дополнительно семантика разошлась с host-эталоном `nodes/src/p.rs`:

- хост считает только rising edge (0→1, есть `last_level`);
- окно анти-двойного у хоста привязано к последнему *посчитанному* событию (`last_counted`, не продлевается), у прошивки — скользящее (`last_edge_ms` продлевается каждым bounce, `<=` вместо `<`).

Тест `low_levels_never_count` есть, теста на удерживаемый высокий уровень нет.

## Почему важно

Node P — метрика Performance: систематический overcount деталей.

## Предлагаемое исправление

- Хранить `prev_level`, считать только на `level && !prev_level`.
- Окно — от последнего посчитанного события (`t_ms.wrapping_sub(last) < debounce_ms`), как в хосте.
- Тест «held high 200 ms → ровно 1».
- После фикса — property-style трасса `bounce/held-high/wrap` против host `nodes::p::EdgeCounter` на одинаковых входах (заявленная «зеркальность»).
