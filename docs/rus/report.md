# OEE-стенд на TinyML: цифровой двойник — отчёт

> Итоговый отчёт по проекту курса (6 недель). План: [`plan.md`](plan.md);
> недельные гейты: [`week1-gate.md`](week1-gate.md) …
> [`week6-gate.md`](week6-gate.md). Числа ниже воспроизводимы: у каждой
> таблицы названа команда-источник. Хост: rustc 1.96.1, linux x86_64;
> QEMU 7.2.22 (`lm3s6965evb`).

## 1. Задача одним абзацем

Цифровой двойник производственной линии измеряет
**OEE = Availability × Performance × Quality** тремя TinyML-узлами: узел A
классифицирует ток станка (1D-CNN: idle/run/jam/overload), узел P считает
детали по событиям ИК-барьера конвейера, узел Q выносит вердикт по звуку
простукивания (1D-CNN: целая/трещина). Детерминированный симулятор на Rust
генерирует сигналы — истинна известна по построению, двойника можно
оценивать численно. Инференс — через локальный форк
[microflow-rs](https://github.com/matteocarnelos/microflow-rs) и вклад
проекта: **оператор Conv1D** (парсер → кодген → int8-ядро). Железа нет:
MCU-часть эмулируется (QEMU LM3S6965), линия симулируется, всё — код.

## 2. Архитектура (что построено)

```text
[line-simulator: сидирован] ──ток──▶ [узел A: 1D-CNN]  ──▶ oee/line1/a/state
  FSM станка, конвейер,      ──ИК──▶ [узел P: фронты] ──▶ oee/line1/p/count
  синтез стука (WAV-подобный) ─стук▶ [узел Q: 1D-CNN]  ──▶ oee/line1/q/verdict
                                                              │
                          [oee-aggregator: окна по watermark, A×P×Q]
                                                              │
                          [oee-dashboard: ratatui TUI, живые гейджи]
```

Шесть крейтов воркспейса OEE (`line-simulator`, `features-cli`, `nodes`,
`mqtt-min`, `oee-aggregator`, `oee-dashboard`), ML-конвейер (`ml/trainer`
на burn, `ml/exporter`: свой PTQ и писатель TFLite-flatbuffers — модели
рождены в Rust, Python в цикле воспроизведения нет) и форк движка
(`fork/microflow`). Седьмой крейт `qemu/` — прошивка недели 6 под LM3S6965
(не член воркспейса: пакет под `thumbv7m`).

Ключевые решения, благодаря которым числам можно верить:

- **Один источник фич**: `features-cli` считает фичи и для обучения, и для
  инференса; модели потребляют сырые окна, фичи — инструмент анализа и
  страховка паритета.
- **ML-конвейер детерминирован целиком**: один сид → бит-идентичный
  `.tflite` (sha256 закреплён в `ml/models/model_a.metrics.txt`).
- **Вклад в движок живёт в форке** с золотыми тестами, без upstream-PR
  (план, раздел 12).

## 3. Вклад в движок (форк)

**Conv1D end-to-end** — та же вертикаль, что у автора движка
(парсер → кодген → рантайм), сперва спецификация
([`fork/docs/conv1d-spec.md`](../../fork/docs/conv1d-spec.md)):

1. **Факт сериализации (спайк недели 1)**: Keras `Conv1D` попадает в TFLite
   как `CONV_2D` над тензором `(1, T, C)` за цепочкой Reshape.
2. **Ядро (неделя 2)**: int8-скалярные произведения вдоль оси времени,
   int32-аккумулятор в единицах смещения, поканальный requant,
   округление к чётному, сатурация при приведении; Same-паддинг явной
   геометрией окон. 96 золотых фикстур (12 форм × 8 вариантов) закрепляют
   результат **бит-в-бит** против наивного эталона
   (`fork/microflow/tests/golden/`).
3. **Парсер/кодген (неделя 3)**: свёртка форм (график спайка: 18 операций
   → 6 слоёв; `EXPAND_DIMS`/`RESHAPE`/`SHAPE`/… кода не порождают),
   нормализация rank-3 входа к `Buffer2D<f32, T, C>` и 1-D-дискриминатор:
   `CONV_2D` компилируется в `conv_1d` ровно когда высота фильтров 1 И
   эффективная высота входа 1.
4. **Добавка недели 6 — вынос zero-point**: исходное ядро считало
   `(x − zx)(w − zw)` на каждый элемент. Бенчмарк (раздел 5) показал, что
   так ядро проигрывает общему пути, и аккумулятор перешёл на точное
   целочисленное разложение `Σxw − zx·Σw − zw·Σx + M·zx·zw` (префикс-суммы
   для краёв Same-паддинга, статические границы цикла в ветке полного
   окна). Золотые фикстуры проходят **бит-в-бит** — округления не
   сдвинулись, поменялся только порядок вычислений.

Цепочка проверки: золотые фикстуры (ядро, бит-в-бит) → паритет с float-
интерпретатором экспортера (модель целиком, ≤2 кванта/слой, ±1 end-to-end)
→ паритет хост/QEMU (раздел 6, бит-в-бит) → эксперимент недели 5.

## 4. Корректность двойника (главный численный результат)

Четыре сценария недели 5, одна команда:
`cargo test -p oee-aggregator --test experiment -- --nocapture`
(подробности: [`week5-gate.md`](week5-gate.md)):

| сценарий | сид | истинный OEE | измеренный | ошибка |
| -------- | --- | ------------ | ---------- | ------ |
| normal   | 42  | 0.841        | 0.841      | +0.000 |
| downtime | 42  | 0.516        | 0.516      | +0.000 |
| slowdown | 42  | 0.612        | 0.612      | +0.000 |
| rejects  | 42  | 0.478        | 0.478      | +0.000 |

**Вывод 1**: в распределении двойник точен — каждая компонента попадает в
свою цель (A 0.61 при простоях, P 0.75 при замедлении, Q 0.55 при
p(брак)=0.5), измеренная сторона повторяет это с ошибкой +0.000. Нули —
работа конструкции (P точен устройством анти-двойного; гистерезис A
сдвигает переходы одинаково; Q в распределении), а не приглаженный бенч.

**Где оно реально ломается** (честная половина результата, свипы
чувствительности D5 недели 5): эпизоды короче `confirm_after × 80 мс`
теряются узлом A (всплеск затора 150 мс невидим при глубине ≥ 3: ошибка
времени работы +150 мс); окно анти-двойного P точно лишь в
[70 мс, ~280 мс] (запас 3–4× вокруг дефолтных 100 мс); Q деградирует
**асимметрично** при сдвиге шума — первым умирает recall трещин, и
измеренный Q завышает качество (1.00 при истинных 0.72 на σ=0.12).

Качество самих моделей (валидационные сплиты, сид 2026;
`ml/models/model_{a,q}.metrics.txt`):

| модель | окон | val-точность (float) | val-точность (int8) |
| ------ | ---- | -------------------- | ------------------- |
| A      | 2235 | 1.0000               | 1.0000              |
| Q      | 171  | 1.0000               | 1.0000              |

Риск «слишком хороших моделей» (план, раздел 11) реализовался и ограничен
таблицами чувствительности, а не спрятан: классы разделены амплитудами по
построению (огибающие 0.4/2.0/3.2/4.5 А), поэтому гауссов шум не сдвигает
узел A вплоть до 5× обучающего уровня.

## 5. Скорость движка (Conv1D против трюка reshape)

Одна команда: `cargo bench --bench conv1d` в `fork/microflow` (плюс
`MICROFLOW_CONV2D_ONLY=1` в отдельном target-dir для строк трюка).
Медианы criterion, хост:

| бенчмарк                    | conv_1d    | conv_2d (трюк) | ускорение |
| --------------------------- | ---------- | -------------- | --------- |
| слой 1: 128×1, k3, f8       | 4.04 мкс   | 4.14 мкс       | 1.02×     |
| слой 2: 63×8, k3, f16       | 4.89 мкс   | 15.02 мкс      | 3.07×     |
| модель A `predict()` (128)  | 14.06 мкс  | 23.54 мкс      | 1.67×     |
| модель Q `predict()` (1024) | 107.95 мкс | 186.05 мкс     | 1.73×     |

Min/avg/max на 20 тысячах прогонов (`cargo run --release --example
latency`): модель A min 15.0 / avg 15.4 мкс, модель Q min 119.0 /
avg 120.5 мкс.

**Вывод 2**: выделенное ядро выигрывает **1.67–1.73×** end-to-end на
реальных моделях узлов — вклад даёт широкий второй слой (там 3.07×); узкий
первый слой тривиален по вычислениям, пути равны (1.02×). Результат не
даром: первая реализация *проигрывала* на 16–20%, пока поправки zero-point
не были вынесены из цикла (раздел 3.4) — бенчмарк поймал дыру в собственном
вкладе проекта.

**Цена скорости** (flash на LM3S6965, следующий раздел): +2.8 КиБ против
трюка — двухветвевые развёрнутые циклы и таблицы префикс-сумм. На 256 КиБ
это 1.1% flash.

## 6. Портабельность и footprint (QEMU, LM3S6965)

Одна команда: `scripts/qemu-parity.sh` →
`PARITY OK: 4 windows, bit-for-bit` — прошивка (та же `model_a.tflite`,
скомпилированная под Cortex-M3) и хост-эталон печатают идентичные биты
вероятностей на фиксированных окнах:

```text
win 0: label=0 argmax=0 idle probs=[0.996 0.000 0.000 0.000] bits=[0x3f7f0000 …]
win 1: label=1 argmax=1 run  probs=[0.000 0.996 0.000 0.000] …
```

**Вывод 3**: целочисленная семантика детерминирована между архитектурами —
хост x86_64 и Cortex-M3 дают одинаковые биты; именно это значит
«портабельность» для int8-движка (и на этом стоит воспроизводимость
двойника).

Одна команда: `scripts/footprint.sh` (сперва все три варианта запускаются
на плате; строки conv2d сверяются с предсказаниями conv1d):

| вариант             | flash Б | flash КиБ | статическая RAM Б |
| ------------------- | ------- | --------- | ----------------- |
| модель A, conv_1d   | 46396   | 45.3      | 0                 |
| модель A, conv_2d   | 43576   | 42.6      | 0                 |
| dense-пол (игрушка) | 30328   | 29.6      | 0                 |

**Вывод 4**: узел A помещается в **45.3 КиБ flash / 0 Б статической RAM**
(18% из 256 КиБ flash LM3S6965; рабочий стек — единицы КиБ активаций — в
ELF не входит, 64 КиБ SRAM его поглощают). Строка «dense-пол» —
сериализационная игрушка недели 1 (случайные веса, вход из 8 значений):
она ограничивает стоимость движка-с-прошивкой без conv-ядра (~29.6 КиБ),
то есть два conv-слоя с данными стоят ~15.7 КиБ, из которых премия за
скорость выделенного ядра — 2.8 КиБ.

## 7. Детерминизм

- Один сид → идентичный повтор эксперимента: тест недели 5
  `same_seed_produces_an_identical_result` сверяет весь windows-CSV
  бит-в-бит (кроме `run_id`) двух прогонов с тремя гоняющимися потоками
  издателей.
- Конвейер обучение→PTQ→экспорт повторяется бит-идентично (sha256).
- Паритет хост/QEMU (раздел 6) — одни и те же биты на двух ISA.

## 8. Ограничения (честно)

- **QEMU не циклоточен** — таймингов MCU из него не берутся; таблица
  скорости — хостовый criterion. QEMU доказывает портабельность и footprint.
- **Драйвер UART рассчитан на стартовое состояние QEMU** (UART0 тактирован
  и подключён; без мультиплексирования GPIOA и включения UART) — реальный
  кремний требует инициализации платы.
- **Нулевая ошибка OEE — правда распределения**: честные каналы ошибки —
  временной (эпизоды короче `confirm_after`), запасы окна P и асимметричная
  деградация Q при сдвиге шума.
- Петлевой брокер — QoS 0 без ретенций/персистентности: для стенда
  достаточно, для производства нет.
- Строка dense — замер размера, а не обученная dense-базлайн (для неё в
  тренер нужен `ModelDense` — будущая работа).

## 9. Будущая работа (план, раздел 12)

Реальное железо (`SensorSource` → `AdcSource`/`I2sSource`, стенд куплен);
PR Conv1D в upstream после курса; узел на OV2640; `MaxPool2D` как вторая
вертикаль движка; QAT, если упадёт точность int8; Grafana с историей;
исследование порога подтверждения/PR-кривой для Q, которое напрашивается
из найденной асимметрии.
